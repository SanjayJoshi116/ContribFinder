Software Requirements Specification (SRS)
GitHub Contribution Discovery & Repository Recommendation Platform

Working Name: ContribFinder
Document Version: 2.0
Status: Proposed
Preferred Stack: Django + Django REST Framework + Python + React + TypeScript

1. Product Overview
1.1 Problem

Developers interested in open-source contribution frequently struggle to:

Find repositories aligned with their technical skills.
Discover projects that are actively accepting contributions.
Determine whether their experience is appropriate for a project.
Find suitable issues among thousands of repositories.
Understand an unfamiliar repository quickly.
Identify projects matching their interests even when terminology differs.
Distinguish beginner-friendly opportunities from issues requiring substantial domain knowledge.
Determine why a particular repository or issue is relevant to them.

ContribFinder addresses this by building a structured developer profile from GitHub data and using it to discover, analyze, and rank potential open-source contribution opportunities.

The system should answer:

"Given this developer's demonstrated skills, experience, interests, and contribution history, which open-source projects and contribution opportunities are relevant for them?"

It should not merely search for repositories containing keywords found in the developer's README.

2. Product Goals
2.1 Primary Goals

The system shall:

Allow users to authenticate using GitHub.
Retrieve relevant GitHub profile information.
Retrieve and analyze the user's profile README where available.
Analyze the user's public repositories.
Analyze programming languages used by the user.
Analyze repository topics and dependencies where available.
Analyze relevant public contribution activity.
Construct a structured developer profile.
Extract technical skills and interests.
Assign confidence to detected skills based on evidence.
Discover potentially relevant open-source repositories.
Analyze candidate repositories.
Rank repositories based on developer-project compatibility.
Explain why repositories were recommended.
Identify potentially relevant contribution opportunities.
Allow users to filter recommendations.
Allow users to save or dismiss recommendations.
Collect user interaction feedback.
Periodically refresh GitHub-derived information.
Allow users to delete their ContribFinder data.
3. Secondary Goals

Future versions may:

Recommend specific "good first issue" opportunities.
Recommend documentation contributions.
Recommend testing opportunities.
Estimate contribution difficulty.
Detect inactive or archived projects.
Analyze repository contribution practices.
Track contribution progress.
Notify users about newly relevant issues.
Generate personalized contribution plans.
Explain unfamiliar repository components.
Recommend projects based on learning goals.
Recommend projects based on career-development goals.
Learn personalized ranking preferences from user feedback.
4. Non-Goals

The MVP shall not:

Automatically create pull requests.
Automatically modify repositories.
Automatically submit GitHub issues.
Automatically communicate with maintainers.
Guarantee that a contribution will be accepted.
Guarantee that a repository is actively maintained.
Predict employment or hiring outcomes.
Predict whether a developer will successfully contribute.
Fully understand arbitrary source code.
Replace GitHub's repository or issue-management functionality.
Automatically make decisions on behalf of the developer.

6. Product Principles

The system should follow these principles.

6.1 Evidence Over Keywords

A technology mentioned once in a README should not be treated the same as a technology repeatedly used in repositories and contributions.

6.2 Explainability Over Black-Box Ranking

Recommendations should explain the evidence behind them.

6.3 Candidate Generation and Ranking Are Separate

The system should first identify potentially relevant repositories and then rank them.

6.4 Activity Signals Are Not Absolute Repository Health

The system should present activity indicators rather than declaring a repository "good" or "bad."

6.5 Ranking Is Not a Guarantee

A recommendation score represents algorithmic relevance, not probability of successful contribution.

6.6 User Control

Users should be able to:

Filter recommendations.
Save recommendations.
Dismiss recommendations.
Refresh their profile.
Disconnect GitHub.
Delete their data.

11. Profile README

The system shall attempt to identify and retrieve the user's GitHub profile README.

The expected convention is the user's profile repository matching their GitHub username.

The system shall:

Detect whether the profile README exists.
Retrieve its contents where accessible.
Parse relevant sections.
Extract technical skills.
Extract interests.
Extract domains.
Extract experience-related signals.
Preserve the original README separately from derived data.

The absence of a profile README must not prevent the user from using the system.

14. Skill Evidence Model

Evidence strength shall be configurable.

Conceptually:

Evidence	Relative Strength
README mention	Low
Repository topic	Low–Medium
Repository language	Medium
Dependency usage	Medium–High
Commit history	High
Pull request	Very High
Repeated contribution	Very High

These values shall be configuration rather than permanent product rules.

The system shall avoid treating an isolated README mention as equivalent to sustained practical usage.

15. Skill Confidence

Candidate Generation

Find potentially relevant repositories.

↓

Candidate Filtering

Remove repositories that are clearly unsuitable.

↓

Candidate Ranking

Rank remaining repositories based on relevance.

This architecture allows candidate-generation strategies and ranking algorithms to evolve independently.

28. Recommendation Engine

The recommendation engine shall use a hybrid architecture.

Stage 1 — Candidate Generation

Identify potentially relevant repositories.

Stage 2 — Deterministic Matching

Calculate signals such as:

Skill match
Language match
Framework match
Interest match
Difficulty fit
Activity signals
Contribution opportunity signals
Stage 3 — Semantic Matching

Use embeddings for:

Developer profile
Repository descriptions
README content
Issues
Interests
Stage 4 — Ranking

Combine the signals using configurable weights.

29. Recommendation Signals

A recommendation may use:

Signal	Description
Skill Match	Compatibility with demonstrated skills
Language Match	Programming language overlap
Framework Match	Framework/tool overlap
Interest Match	Alignment with stated or inferred interests
Semantic Match	Meaning-level similarity
Difficulty Fit	Compatibility with contribution experience
Activity Signal	Recent observable repository activity
Issue Fit	Availability of potentially relevant contribution opportunities

No single signal should automatically determine the recommendation.

30. Recommendation Configuration

Recommendation weights shall be configurable.

The initial values are experimental and must not be treated as product truth.

The system should support:

Global default weights
Versioned scoring configurations
Experimentation
Evaluation against benchmark datasets
Future user-specific weighting

Every generated recommendation should record which scoring configuration produced it.

31. Recommendation Score

The score shall be treated as an internal ranking signal.

The UI should avoid implying:

"This repository is 87% suitable for you."

Instead, it may display:

"Strong match"

and provide the evidence behind that classification.

If a numeric score is exposed, it should be clearly described as a ranking score rather than probability, expertise, or contribution success.

32. Recommendation Explanation

Every recommendation shall contain machine-readable reasons.

Possible reason types:

Skill
Language
Framework
Interest
Domain
Activity
Difficulty
Issue availability

Example:

Why this repository matches:

• Python is strongly represented in your development history.
• The project uses Django.
• The repository aligns with your developer-tooling interest.
• Several potentially relevant backend issues are available.

The explanation should be generated from actual scoring evidence.

The system must not invent reasons that were not supported by the recommendation pipeline.

33. Semantic Matching

Embeddings shall be used to capture semantic relationships.

For example:

Developer interest:

Developer productivity

Repository:

Tools for improving engineering workflows

may be considered semantically related even without exact keyword overlap.

Embeddings should complement deterministic signals rather than replace them.

85. Important Architectural Decisions

The following decisions are considered foundational:

Decision 1

Modular monolith before microservices.

Decision 2

PostgreSQL + pgvector before introducing a dedicated vector database.

Decision 3

Celery + Redis for long-running GitHub and AI processing.

Decision 4

GitHub data synchronization rather than GitHub API calls on every request.

Decision 5

Candidate generation and ranking are separate pipeline stages.

Decision 6

Deterministic scoring remains responsible for final ranking.

Decision 7

LLMs assist extraction and classification rather than controlling recommendations.

Decision 8

Recommendation explanations are first-class data.

Decision 9

Recommendation weights are configuration, not hard-coded product truth.

Decision 10

Repository activity is presented as observable signals rather than an absolute health score.

87. Final Product Direction

The most important distinction in ContribFinder is:

It is not a GitHub repository search engine.

It is a developer-to-contribution opportunity matching system.

The core product loop should therefore remain:

UNDERSTAND DEVELOPER
        ↓
FIND CANDIDATES
        ↓
UNDERSTAND PROJECTS
        ↓
MATCH DEVELOPER ↔ PROJECT
        ↓
EXPLAIN MATCH
        ↓
IDENTIFY CONTRIBUTION OPPORTUNITIES
        ↓
LEARN FROM INTERACTION
        ↓
IMPROVE RECOMMENDATIONS
