Software Requirements Specification (SRS)
GitHub Contribution Discovery & Repository Recommendation Platform
Working name: ContribFinder
Document version: 1.0
Preferred stack: Django + Django REST Framework + Python + React + TypeScript
Primary goal: Analyze a developer's GitHub profile/README and recommend open-source repositories where they are likely to make meaningful contributions.

1. Product Overview
1.1 Problem
Developers often want to contribute to open source but struggle with:

Finding projects aligned with their skills.

Knowing whether a repository actually needs contributors.

Determining whether they have enough experience for a project.

Finding suitable issues among thousands of GitHub repositories.

Understanding a repository's technology stack from its README.

Connecting their own skills/interests with repositories.

Distinguishing beginner-friendly issues from issues requiring deep domain knowledge.

The proposed application solves this by building a developer profile from GitHub data and matching it against repositories, issues, and project documentation.

1.2 Core idea
A user provides:

GitHub username / GitHub OAuth

The application analyzes:

GitHub Profile

The important distinction is that the system should not simply search for repositories containing technologies mentioned in the README.

It should answer:

"Given what this developer knows and appears interested in, which open-source projects and specific contribution opportunities are worth exploring?"

2. Goals
2.1 Primary goals
The system shall:

Allow users to connect their GitHub account.

Retrieve and analyze their GitHub profile README.

Analyze their public repositories and programming languages.

Build a structured developer skill profile.

Discover potentially relevant GitHub repositories.

Analyze repository README files and metadata.

Analyze open issues and contribution labels.

Calculate a compatibility score between the developer and repositories.

Explain why a repository was recommended.

Recommend specific issues where possible.

Allow users to filter recommendations.

Allow users to save/bookmark repositories.

Learn from user feedback.

Periodically refresh GitHub data.

2.2 Secondary goals
Future versions may:

Recommend first issues.

Recommend "good first issue" opportunities.

Analyze contribution difficulty.

Detect inactive repositories.

Detect repositories with healthy contribution activity.

Track contribution progress.

Notify users about newly relevant issues.

Generate personalized contribution plans.

Explain unfamiliar parts of a repository.

Recommend repositories based on career goals.

3. Non-Goals for MVP
The first release should not attempt to:

Automatically create pull requests.

Automatically modify repositories.

Automatically submit issues.

Automatically communicate with maintainers.

Replace GitHub.

Guarantee that a contribution will be accepted.

Guarantee that a repository is actively maintained.

Make hiring/employment predictions.

Fully understand arbitrary source code.

These can be considered later.

This is important because GitHub API operations shouldn't block an HTTP request.

GitHub's current REST API documentation states that authenticated requests generally have a 5,000-request/hour primary limit, while unauthenticated requests have a 60-request/hour limit; search endpoints have additional restrictions. The system should therefore aggressively cache and synchronize data asynchronously.

15. Skill Confidence Model
Do not treat:

"Python"

in a README as equivalent to:

500 commits in Python repositories

Instead assign evidence weights.

Example:

Evidence	Weight
README mention	0.20
Repository topic	0.30
Repository language	0.50
Dependency usage	0.60
Commit history	0.80
Pull request	0.90
Repeated contribution	1.00

These are initial heuristic values and should be configurable.

22. Recommendation Engine
I recommend a hybrid recommendation architecture.

Phase 1 — Rule-based scoring
Start simple.

RecommendationScore =
    SkillMatch
  + InterestMatch
  + LanguageMatch
  + FrameworkMatch
  + IssueAvailability
  + ActivitySignal
  + DifficultyMatch
  + ContributionFit

Example:

Skill match             30%
Interest match          20%
Technology match        15%
Issue availability      10%
Difficulty fit          10%
Repository activity     10%
Contribution openness    5%

These should be configurable.

23. Phase 2 — Semantic Matching
Generate embeddings for:

Developer profile
Repository README
Repository description
Issues
Topics

Then calculate:

cosine_similarity(
    developer_embedding,
    repository_embedding
)

This catches semantic relationships such as:

Developer:
"Interested in developer productivity"

Repository:
"CLI tooling for improving engineering workflows"

even though the exact words differ.

24. Phase 3 — Hybrid Ranking
Final recommendation score:

FinalScore =
    0.50 * SemanticSimilarity
  + 0.30 * SkillMatch
  + 0.10 * DifficultyFit
  + 0.10 * ActivitySignal

Do not hard-code these values permanently.

Create a scoring configuration:

RECOMMENDATION_WEIGHTS = {
    "semantic": 0.50,
    "skills": 0.30,
    "difficulty": 0.10,
    "activity": 0.10,
}

Later you can tune them using user feedback.

Instead:

GitHub
   │
   ▼

   │
   ▼
PostgreSQL
   │
   ▼
API
   │
   ▼
React

Example:

User visits dashboard
        │
        ▼
Read PostgreSQL
        │
        ▼
Return recommendations

Meanwhile:

Periodic Celery job
        │
        ▼
Check GitHub
        │
        ▼

        │

This also reduces API usage.

45. AI / LLM Architecture
I would not make an LLM responsible for the entire recommendation system.

Use deterministic algorithms where possible.

LLM responsibilities
Good uses:

README → skill extraction
README → interest extraction
Issue → contribution type
Issue → difficulty classification
README → summary
Repository → semantic description

Algorithmic responsibilities
Use traditional scoring for:

skill matching
language matching

61. MVP Recommendation Algorithm
Start with:

score = (
    0.35 * skill_similarity +
    0.25 * semantic_similarity +
    0.15 * language_similarity +
    0.10 * interest_similarity +
    0.10 * activity_score +
    0.05 * issue_fit
)

Normalize every component to:

0.0 → 1.0

Then:

recommendations = sorted(
    candidates,
    key=lambda x: x.score,
    reverse=True
)

The exact weights should be treated as tunable configuration, not product truth.
